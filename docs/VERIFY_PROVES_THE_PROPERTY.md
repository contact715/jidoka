# Проверка доказывает само свойство, а не его тень

Правило, установлено 2026-09-29. Класс ошибки `green-check-that-checks-nothing`.

Проверка утверждает то свойство, ради которого её пишут: нужное значение есть и оно
непустое, нужное правило стоит в файле. Совпавший счёт побочных эффектов не доказывает
ничего. Две пустоты между собой не сравниваются: **пустое никогда не равно пустому**, а
значит, сравнение двух пустых ответов даёт «не проверено», а не «совпадает».

## Откуда правило

2026-09-25, сайт A+ Heating & Air, одна сессия, три зелёных вердикта без проверки.

1. Репетиция переноса сверяла значения двух баз так: `[ "$(q a)" = "$(q b)" ]`. В обоих
   запросах было неверное имя колонки. Оба упали, `$(...)` вернул пустые строки (текст
   ошибки ушёл в поток ошибок и в сравнение не попал), и скрипт напечатал «совпадает».
2. Скрипт правки конфига сервера доказывал себя строкой
   `assert s.count('include ...') == 6`. Шесть вхождений набралось за счёт другой замены,
   а правила, ради которых всё делалось (страницы 404 и редиректы 301), так и не встали.
3. В реестре ошибок за тот же день: сверка «репозиторий против сервера» не выполнила
   серверную часть (экранирование в ssh), сравнила 0 файлов и выдала «совпадает».

Во всех трёх случаях вердикт опирался на ноль проверенного. Проверка мерила то, что
легко посчитать, а не то, о чём был вопрос.

## Три формы одной ошибки

| Форма | Что мерили | О чём был вопрос |
|---|---|---|
| пусто равно пусту | совпадение двух строк | совпадают ли ЗНАЧЕНИЯ |
| счёт вместо наличия | число вхождений шаблона | стоит ли НУЖНОЕ правило |
| ноль сравнённого | отсутствие найденных различий | сравнили ли хоть что-то |

## Как проверять

Помощник лежит в `scripts/lib/verify.mjs` (в установленной копии
`~/.claude/jidoka/scripts/lib/verify.mjs`). У него два режима.

**Сравнить два значения** (bash):

```bash
A=$(psql "$DB_A" -tAc "select count(*) from pages")
B=$(psql "$DB_B" -tAc "select count(*) from pages")
node ~/.claude/jidoka/scripts/lib/verify.mjs same --a "$A" --b "$B" || exit 1
```

**Доказать, что правка вставила нужное** (после любого скрипта правки, на любом языке):

```bash
node ~/.claude/jidoka/scripts/lib/verify.mjs present --file /etc/nginx/sites-enabled/site.conf \
  --needle 'error_page 404 /404.html' --needle 'return 301 https://'
```

Недостающие фрагменты перечисляются поимённо. Искать надо ровно то, ради чего правка
делалась, а не общий шаблон, который может встретиться и в чужой замене.

**Из JavaScript:**

```js
import { sameNonEmpty, requirePresent } from '../lib/verify.mjs';
sameNonEmpty(a, b);                       // 'equal' | 'different' | 'unverified'
requirePresent(conf, ['error_page 404']); // список недостающих; [] значит всё на месте
```

**Из Python без node** тот же приём в две строки. Важен непустой список искомого:

```python
NEEDED = ['error_page 404 /404.html', 'return 301 https://']
missing = [n for n in NEEDED if n not in s]
assert NEEDED and not missing, f'не встало: {missing}'
```

Коды выхода: 0 значит равно или всё на месте, 1 значит различается или чего-то нет,
**3 значит НЕ ПРОВЕРЕНО**, 2 значит неверный вызов (ничего не выполнено). Код 3 отдельный
намеренно: «не смогли проверить» и «проверили и нашли расхождение» требуют разных действий.

## Что считается «не проверено»

- значение не передано, пустое или из одних пробелов;
- заглушка вместо значения: `null`, `undefined`, `None`, `NaN`, `(null)`, `(0 rows)`;
- след упавшей команды в начале строки: `ERROR:` и `FATAL:` (psql, mysql), `error:` и
  `psql: error:`, `Parse error:`, исключение вида `sqlite3.OperationalError:`,
  `Traceback (most recent call last)`, `curl: (6)`, `command not found`,
  `No such file or directory`, `Permission denied`;
- объект вместо текста: `String()` превратил бы любые два объекта в одинаковое
  `[object Object]`;
- для `present`: файл не прочитан или пуст. Пустой список искомого и пустой фрагмент
  считаются ошибкой вызова, потому что пустая строка «находится» в любом тексте.

Края строки (пробелы, перевод строки) при сравнении не учитываются: psql печатает число с
пробелом впереди, `$(...)` срезает перевод строки в конце.

Слово error внутри значения ошибкой не считается: `error_count=0`, `error_page 404`,
`no errors` сравниваются как обычный текст.

## Известная граница

Законное значение, которое само начинается со следа ошибки (статус задачи `ERROR`, ключ
YAML `error: 404`), помощник назовёт непроверенным. Это отказ в громкую сторону, и он
выбран сознательно: ложное «не проверено» видно сразу, ложное «совпадает» не видно никогда.
В таком случае сравнивайте другое представление того же факта, например
`status = 'ERROR'` как `t`/`f`. Хеш текста не подходит: хеш двух одинаковых ошибок тоже
совпадёт.

## Чего помощник не делает

Это средство, а не сторож. Его не вызывает ни хук, ни CI, поэтому метки `@closes-class`
у него нет: класс закреплён за `scripts/oracle-divergence.mjs` (решение владельца
2026-09-29, то же рассуждение в `docs/RESEARCH_TIERS.md`: второй маркер сказал бы реестру,
что класс закрыт везде). Пользоваться помощником обязывает правило в глобальном CLAUDE.md,
а не механизм. Если класс повторится на самодельной проверке, следующий шаг описан и
оценён: мягкий хук перед записью или запуском скрипта, который узнаёт сравнение двух
`$(...)` и `assert` на `count` и предлагает этот помощник.

## Попутная починка в приборе реестра

`gate-audit.mjs` считал механизм подключённым, если имя его файла встречалось где угодно
в настройках, хуках или CI, в том числе внутри чужого имени. Файл `verify.mjs` в папке
`scripts` был бы засчитан подключённым из-за строки `adaptive-verify.mjs`, хотя его никто
не вызывает. На живых данных нашёлся реальный случай: `reasoning-bank.mjs` считался
подключённым только потому, что CI запускает `test-reasoning-bank.mjs`. Теперь имя должно
стоять отдельно (`wiredSetFrom`, две новые самопроверки). Отчёт реестра до и после
починки совпал строка в строку: у `reasoning-bank.mjs` нет метки класса.

## Проверено

- `node scripts/lib/verify.mjs --self-test`: 22 проверки;
- `node --test scripts/__tests__/verify-lib.test.mjs`: 9 тестов, скрипт запускается
  настоящим процессом, потому что встроенная самопроверка зовёт функции напрямую и не
  видит поломки точки входа;
- три нарочные поломки в копии (пустое не проверяется, нет стража пустого фрагмента,
  следы ошибок не распознаются): все три пойманы самопроверкой, первая в живом запуске
  дала тот самый ложный «равно»;
- `import-safety`, `cli-strictness` и договор CLI в песочнице зелёные для нового файла.
