# Замер: как скрипты движка разбирают аргументы — 2026-09-16

Класс `extra-argument-silently-swallowed`. Правило и механизмы: `docs/CLI_STRICTNESS.md`.

## Как мерили

Замер статический: ни один скрипт при нём не запускался, потому что запуск с незнакомым
флагом и есть измеряемая опасность. Прибор `scripts/cli-strictness.mjs` читает текст файла.
Для каждого модуля в `scripts/`, `hooks/`, `global-setup/` он определяет три вещи:

- способ разбора аргументов: помощник `scripts/lib/cli.mjs`, `util.parseArgs` (строгий или нет),
  свой цикл, поиск подстроки, «аргументы не читаются»;
- отказывает ли скрипт на незнакомом флаге;
- побочные действия: запись в git, запуск агента, удаление, сеть, сигналы процессам, запись
  файлов, запуск команд. Строки-сообщения, регулярные выражения и действия внутри самопроверки
  учитываются отдельно.

Таблица «до» снята с основного клона движка на коммите `a9cdf7f`: это main перед переводом скриптов.
Номера строк в ней относятся к тому состоянию.
Числа «после» сняты с итогового дерева той же командой:

```
node scripts/cli-strictness.mjs --all --report <файл>
```

## Что делал `--help` до перевода (выборка из отчётов исполнителей)

Поиск подстроки не просто пропускал незнакомый флаг. Для многих скриптов `--help` был обычным
запуском со всеми побочными действиями:

- `chaos-inject.mjs` — все пять инъекций сбоев;
- `run-mutation.mjs` — прогон, который переписывает исходники в `lib/`;
- `snapshot-global.mjs` — перезапись папки `global-setup/`;
- `run-container-scan.mjs` — полный скан trivy с записью в реестр находок;
- `safe-commit.mjs` — коммит и пуш в main (исходный случай).

И опечатки во флагах, которые включали опасный режим:

- `generate-api-types.mjs`: опечатка в `--check` включала запись файла;
- `detect-constitutional-drift.mjs`: опечатка в `--dry-run` включала боевой режим;
- `auto-strengthen.mjs`: при `--apply --dry-run` побеждал `--apply`;
- `permission-ledger.mjs grant x --scope` без значения выдавал разрешение с областью `*`;
- `claim-wave-id.mjs --brnach dev` отправлял резерв номера в ветку по умолчанию;
- `jidoka.mjs relay --self-test` запускал самопроверку диспетчера, а не relay.

## Что нашлось по дороге

Всё ниже найдено приборами этой работы или исполнителями при переводе. Починено, если не сказано иное.

1. **CI на main был красным с 2026-09-14.** Кейс eval «sibling-parity/red-one-of-three» звал хук из
   `$HOME/.claude/hooks`, которого на сервере нет. Хук перенесён в канон, кейс зовёт его из
   репозитория (коммит `e50f0ca`; параллельная сессия затем довела поиск механизма, `bf4ca91`).
2. **Работа при импорте, которую пропускал статический `import-safety`.**
   `current-wave-status.mjs` трижды вызывал `execSync` (ошибки глотались), `dashboard/serve.mjs`
   создавал HTTP-сервер, `test-reasoning-bank.mjs` создавал временную папку. Ещё у двух десятков
   модулей чтение argv и реестра ошибок стояло на верхнем уровне. Всё перенесено под сторож.
   Теперь живая проверка импорта всех модулей в песочнице стоит в `cli-contract.test.mjs`.
3. **Установка не везла общие модули.** Проверка замкнутости импортов в `install-into --self-test`
   видела только ./x.mjs и была бы зелёной над установкой без `./lib/cli.mjs`; `install-global.sh`
   не копировал `scripts/lib/` и `hooks/lib/`. Починено, у проверки замкнутости есть свой кейс.
4. **Мёртвый гейт в pre-commit.** Блок `cyrillic-boundary` использовал `$staged_mjs` до объявления
   и не срабатывал ни разу с коммита `0f2c494`.
5. **Проверки приёмки, которые ничего не проверяли.**
   - `meta-gate-registry.md` AC-1: `meta-remedies.mjs --self-test` — у модуля нет ни входа, ни
     самопроверки, команда выходила с 0. Теперь AC-1 — `node --test scripts/__tests__/meta-audit.test.mjs`.
   - `gdoc-export.md` AC-1 звал `dashboard/serve.mjs --self-test`: ветки самопроверки там нет,
     и вызов поднял бы сервер. Теперь — `dashboard/gdoc-export.mjs --self-test`.
   - `cross-line-dispatch-guard.md` AC-1 звал флаг `--self-check`, которого скрипт никогда не читал;
     код 1 совпадал с ожидаемым случайно. Теперь это описание фикстуры, как у соседнего AC-2.
   Сверка мест вызова теперь считает сломанным любой вызов модуля без точки входа с аргументами.
6. **Мёртвые флаги в живых местах вызова.** Текст задания в `kaizen-dispatch.mjs` велел запускать
   `kaizen-audit.mjs --repo .` (флага нет); шапка `detect-injection.mjs` описывала `--stdin`
   (stdin не читается); шапка `horizon-length.mjs` — `--wave` (не читается). Исправлены тексты.
7. **Запись в реестр ошибок молча терялась.** `enforcement-reconcile.mjs` звал `meta-log.mjs` без
   обязательного `--mode`; отказ глушился. Добавлен `--mode FM-3.3`.
8. **Приборы, которые ослепли бы после перевода.** Детекторы самопроверки в `map-ac-coverage.mjs` и
   `selftest-reality.mjs` искали строку `argv.includes('--self-test')`; `mutation-test.mjs` копировал
   мутанта без `./lib/cli.mjs`, и каждый мутант «погибал» на импорте — пустая самопроверка давала 100%;
   `dup-guard.mjs` считал бы каждый `export const CLI` дублем. Все четыре научены новой форме, у
   каждого есть кейс.
9. **Кейсы eval, которые копируют скрипт во временную папку**, теперь везут и `lib/cli.mjs`
   (`memory-supersede`, `map-ac-coverage`, `compaction-trace`); без этого они краснели на импорте, а
   не на проверяемом свойстве.
10. **Независимое ревью** (пять рецензентов: четыре по переведённым скриптам, один по приборам)
    блокеров не нашло. По приборам — 8 важных дефектов, все закрыты: песочница пропускала отчёт

    текст с `kaizen-audit.mjs --repo .`: с новым разбором каждая упала бы на шаге приёмки. Текст
    исправлен, id и статусы не менялись; 17 выполненных задач не тронуты — это история.

12. **Живой хук `guardrail-tripwire` у владельца не работал ни разу.** Он искал детектор в
    `~/.claude/scripts/` (там лежат чужие скрипты), а детектор установлен в
    `~/.claude/jidoka/scripts/`. Детектор не загружался, хук молча пропускал всё, а самопроверка

    любой другой проверка «обход находит модули движка» краснела. Теперь обход идёт от папки
    модуля, а исключения (`.worktrees`, `fixtures`) сверяются с путём внутри области: корень в такой

## Чего не проверено и почему

- **Вызовы в форме массива** (`spawnSync(node, [SCRIPT, '--x'])`) сверка мест вызова не разбирает.
  Такие места в движке проверены только самопроверками вызывающих скриптов.
- **Правильные вызовы скриптов без самопроверки** не запускались: у многих из них рабочий запуск
  пишет, пушит или шлёт. Поведение сверялось чтением кода, разбором через `parseCli` и ревью диффа.
  Один такой дефект (`validate-dr-catalog`, удалённая переменная) исполнитель поймал живым `--dry`;
  механический поиск удалённых, но используемых имён по всем 278 изменённым модулям других не нашёл.
- **Копии движка в продуктах** (`.jidoka/scripts/` в projectx-app) не обновлялись: их скрипты
  переедут при следующей установке. Три вызова из документации продукта сверены и разбираются.
- **Песочница не видит** прямых привязок (`process.binding`, `internalBinding`), родных модулей, WASI,
  inspector и записи через дескриптор, открытый до её загрузки.
- **Node 20** (версия CI) локально не запускался: здесь Node 24 и 22. По коду несовместимостей нет,
  подтвердит первый прогон CI после пуша.
