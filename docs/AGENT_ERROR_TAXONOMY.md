# Сбой агента это не одно событие, а четыре разных

Происхождение: 2026-08-03, разбор кандидата *umputun/ralphex* по просьбе владельца. До этой
правки у релея была ровно одна ветка на любой ненулевой выход агента:

```js
if (res.status !== 0) {
  updateStatus(... state: 'failed' ...);
  throw new Error(`claude failed with status ${res.status}`);
}
```

Одна строка, один исход. Моргнувший сервер и неверный ключ доступа обрабатывались
одинаково: забег умирал целиком. Живой клиентский прогон мог погибнуть от секундной
недоступности. Пробел был записан неделей раньше как `2026-W31-R6` и висел открытым.

## Четыре вида, а не один

| вид | что это | что делаем |
| --- | --- | --- |
| временный | 529, 502, 503, 504, обрыв соединения, ECONNRESET | повтор с ростом паузы, 5с, 10с, 20с, потолок 60с |
| упор в лимит | «you've hit your limit», 429, исчерпан бюджет | ждём и повторяем, только если ожидание разрешено флагом `--wait` |
| смертельный | 400, 401, 403, 404, 413, 500, нет сессии, нет бинарника | не повторяем никогда, останавливаемся и называем причину |
| неопознанный | всё остальное | останавливаемся и говорим, что не опознали |

Порядок проверки важен: смертельные шаблоны стоят выше временных, чтобы 500 не проглотился
общим правилом про пятисотые.

## Осознанное отличие от источника

ralphex повторяет неопознанные сбои. Мы нет. Голый ненулевой выход у нас гораздо чаще
означает дефект в собственном промпте или в обвязке, чем сетевой сбой. Повтор в этом случае
жжёт токены и прячет ошибку. Поэтому неопознанное останавливает забег и помечается как
неопознанное, чтобы шаблон добавлялся в таблицу по факту, а не по догадке.

Второе отличие: мы не берём сам бинарник. `ralphex` это встречная обвязка на Go, которая
хочет сама владеть сессией и сама звать `claude`. Перенесена только идея, то есть таблица,
и она живёт в нашем языке с нашими самотестами.

## Патовая ситуация

Там же лежит `isStalemate`: если подряд идут N кругов с одинаковым отпечатком результата,
цикл платит за то, чтобы стоять на месте. Отпечаток круга считается из числа открытых
замечаний, отсортированного списка изменённых файлов и сжатого начала вывода, поэтому он не
шумит от порядка файлов и лишних пробелов.

## Где это лежит

- `scripts/agent-error-policy.mjs` — чистые функции, ноль зависимостей, 39 самопроверок.
- `scripts/jidoka-relay.mjs` — подключено в обеих ветках, `claude` и `codex`, плюс внешний
  цикл выдерживает назначенную паузу через `sleepSync`.
- Число попыток: `JIDOKA_RELAY_MAX_ATTEMPTS`, по умолчанию 3. Разрешение ждать при упоре в
  лимит: `--wait <мс>` или `JIDOKA_RELAY_WAIT_MS`.

## Доказательство, живое

Подставной агент, три сценария, реальный запуск релея.

Временная ошибка: агент падает с 529 на первом вызове.

```
jidoka-relay: codex failed (transient: upstream overloaded or gateway error) — transient error, retrying in 5s, attempt 2/3
jidoka-relay: waiting 5s before retrying codex
jidoka-relay: step 2/6 -> codex (codex-retry)
jidoka-relay: done
```
Вызовов агента: 2. До правки забег бы умер на первом.

Смертельная ошибка: 401.
```
jidoka-relay: codex failed (fatal): client-side API error [API Error: 401] — fatal error, retrying cannot help
```
Вызовов агента: 1, повтора нет.

Упор в лимит без разрешения ждать.
```
jidoka-relay: codex failed (ratelimit): account limit reached — rate limited and no wait authorised — stopping cleanly (pass --wait <ms> to sit it out)
```
Вызовов агента: 1, тихой петли нет.

Класс в мета-леджере: `agent-failure-treated-as-single-outcome`.
