# «Такого нет» — только если проверены ВСЕ известные копии кода, не одна удобная

Происхождение: projectx-app (Mosco.ai), 2026-07-31. Владелец спросил про фичу ARCL. Агент
проверил свою память, документы проекта и локальный клон бэкенда `castells-calls` (лежит на
диске, с ним весь сеанс работали) — ничего не нашёл и сказал «такого нет». ARCL реально
существовала и работала в проде: у продукта Mosco оказалось ДВА разных бэкенд-репозитория
(`castells-calls` на GitLab — устаревший, отключённый от push, физически не может подтянуть
новое; *Mosco-corp/back* на GitHub — настоящий, активно пушится). Более того, собственный
справочник проекта (CANONICAL_SOURCES.md, в другом репозитории) прямо называл неверный
репозиторий «реальным API» — агент доверился документу, который сам был неправ. Владелец
поймал это сам, не гейт.

## Правило

Прежде чем сказать «в бэкенде/движке/системе X такого нет» или сделать любое архитектурное
заявление про «как работает продукт» — перечислить ВСЕ известные копии кода этого продукта
(из документов проекта, git remotes, `gh repo list <org>`), а не только ту, что лежит под рукой
локально или с которой уже работали в этой сессии. Одна удобная копия — не источник истины,
если существует другая.

Признаки, что копий может быть несколько:
- в документах проекта упоминаются два разных хостинга (GitLab и GitHub)
  для «одного и того же»;
- есть фраза вида «это тот же код из разных источников» — такое утверждение ДЕКАЕТ со временем
  и не проверяет себя само; если давность утверждения не видна — считать его непроверенным;
- локальный клон не может сделать `git fetch` (отключённый push/pull, протухшие креды) —
  сигнал, что он физически не может догнать реальный источник.

## Как проверить перед заявлением

1. `grep -rn "github.com\|gitlab.com" <корневые доки проекта>` — собрать все репозитории,
   имеющие отношение к продукту.
2. Если их больше одного и оба претендуют быть «бэкендом» — свериться напрямую:
   `gh search code "<термин>" --repo <org>/<repo>` по каждому, не только по первому найденному.
3. Если проектный справочник (canonical-sources-style файл) называет один репозиторий
   единственно верным — не принимать это на веру бесконечно; при малейшем сомнении (давнее
   утверждение, репозиторий не обновлялся, локальный клон не тянется) — перепроверить фактом,
   не документом.
4. Если сомнение подтвердилось — не просто исправить свой ответ, а исправить документ,
   который дал неверный ответ (иначе следующая сессия наступит на те же грабли).

## Композиция

Частный случай «Ресёрч не сдаётся без собственного аудита покрытия»
(`RESEARCH_COVERAGE_SELF_AUDIT.md`) — но применяется не только к формальным ресёрчам, а к ЛЮБОЙ
проверке «есть ли X в системе», даже к быстрому «посмотри есть ли такое». Дополняет
«A specific you inferred is not a fact»: здесь неверной специфике предшествовал неполный набор
источников, а не домысел.

Класс в мета-леджере: `single-repo-assumed-canonical`.
