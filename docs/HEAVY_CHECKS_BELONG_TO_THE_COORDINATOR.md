# Тяжёлую проверку делает координатор, один раз — не каждый агент

Происхождение: projectx-app, 2026-07-28. Волна из десяти агентов правила
дизайн-код по непересекающимся зонам. В задании каждому было написано: «после
правок запусти проверку типов». Десять агентов честно выполнили — шесть полных
проверок проекта пошли одновременно, каждая с растущей кучей. Машина встала,
владелец: «комп тормозит, проверь что убивает и исправь на системном уровне».

Это второй заход одного и того же класса. Первый — 2026-07-24, девять `tsc` по
2.8 ГБ уронили Mac; тогда появился `scripts/tsc-guard.mjs` и общая очередь
`heavy-queue.mjs`. Защита была, и она не сработала.

## Две причины, и обе системные

### 1. Сторож закрывал только парадную дверь

Обёрнут был `node_modules/.bin/tsc`. А агенты звали
`node node_modules/typescript/bin/tsc` — прямой путь, мимо `.bin`, мимо очереди.
Причём звали так, потому что **так было написано в моём же задании**: я скопировал
приём из `tests/_helpers/tscOnce.ts`, где прямой путь выбран НАМЕРЕННО (изнутри
Vitest вызов через обёртку висит, потому что очередь держит сам Vitest).

Вывод, который стоит запомнить: **обходной путь, придуманный ради одного
законного случая, становится дырой для всех остальных.** Если у инструмента есть
второй путь запуска — сторож обязан стоять и на нём, а законный обход должен быть
ЯВНЫМ и проверяемым, а не «звать другой файл».

Как закрыто (`projectx-app`, образец):
- обёрнут и прямой путь `node_modules/typescript/bin/tsc`;
- сторож запускает компилятор через `typescript/lib/tsc.js`, иначе обёртка
  вызывала бы саму себя;
- законный обход — переменная `HEAVY_QUEUE_BYPASS=1`, её ставит только тот, кто
  УЖЕ сериализован собственным замком (`tscOnce.ts`);
- установщик `scripts/install-tsc-guard.mjs` ставит обе обёртки из postinstall,
  потому что npm восстанавливает оригиналы при каждой установке.

Доказательство: три одновременных прямых вызова → работает один компилятор
(замер `pgrep -f 'typescript/lib/tsc.js' | wc -l` = 1).

### 2. Задание агентам требовало невозможного

Даже с идеальным сторожем десять агентов, каждый из которых ждёт своей очереди на
трёхминутную проверку всего проекта, — это полчаса ожидания ради одного и того же
результата. Проверка ВСЕГО проекта не является работой отдельного агента: его
зона — часть, а проверяет он целое.

**Правило для любой многоагентной волны:**

- Агент проверяет только то, что относится к его зоне и стоит дёшево: прочитать
  свой файл, запустить тесты своего модуля, сверить разметку.
- Проверка ВСЕГО — типы, сборка, полный прогон тестов, бюджет бандла, сканеры —
  принадлежит КООРДИНАТОРУ и делается ОДИН раз, после того как все агенты сошлись.
- В задании агенту это пишется прямым текстом: «проверку типов и сборку НЕ
  запускай — их сделает координатор в конце». Иначе агент, старающийся хорошо,
  запустит их сам.
- То же касается dev-серверов: агент не поднимает свой сервер, чтобы «посмотреть».
  Один сервер на волну, поднимает координатор.

## Забытая проверка перед волной

Прежде чем раздать задание N агентам, посчитай цену задания × N. Если в задании
есть шаг, который стоит гигабайт или минуту, он умножится на N и станет тем, что
уронит машину. Дешёвое — агентам, дорогое — координатору.

Классы в мета-леджере: `guard-bypassed-via-alternate-path`,
`every-agent-runs-the-full-check`.

Композируется с `GATES_MUST_SCALE_WITH_THE_CHANGE.md`: там гейт должен стоить
пропорционально ПРАВКЕ, здесь — пропорционально ЧИСЛУ ИСПОЛНИТЕЛЕЙ.
