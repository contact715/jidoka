# Ресёрч — два уровня, один набор инвариантов

Уровень выбирается ВСЕГДА и называется владельцу вслух первой строкой ответа.
«Почитал и рассказал» уровнем не является ни при каких словах запроса.

## 1. Триаж — какой уровень

Считай баллы. Совпало — плюс балл.

| Признак | Балл |
|---|---|
| Владелец сказал «дип», «deep», «от и до», «максимально», «не иди по пути наименьшего сопротивления» | +3 |
| Ответ повлияет на то, что мы будем строить неделями (архитектура, позиционирование, выбор платформы) | +2 |
| Сравнение с внешним продуктом, у которого есть документация | +2 |
| Нужно смотреть НАШ код, чтобы ответить честно | +1 |
| Источников заведомо больше трёх | +1 |
| Ответ уйдёт наружу — клиенту, партнёру, в публикацию | +1 |
| Вопрос про один факт, одну страницу, одну библиотеку | −2 |
| Владелец сказал «быстро», «коротко», «просто посмотри» | −2 |

**0–2 балла → лёгкий уровень. 3 и выше → тяжёлый (дип).**

Пограничный случай (ровно 3) решается в пользу лёгкого, НО с явной строкой владельцу:
«взял лёгкий уровень, если нужно глубже — скажи». Тихо занизить уровень нельзя;
занижение без предупреждения — это класс `research-depth-silently-downgraded`.

Обратное тоже запрещено: гнать тяжёлый прогон на вопрос про одну строку в документации
это не тщательность, а сожжённые полчаса владельца.

## 2. Инварианты — обязательны на ОБОИХ уровнях

Уровни отличаются объёмом, а не честностью. Эти пять держатся всегда.

1. **У каждого внешнего утверждения есть источник и его СИЛА.**
   `первоисточник` (документация вендора, его API, его тарифы, его код) /
   `сторонний` (блог, обзор, сравнительная статья) / `вывод` (я это вывел, никто так не писал).
   Вывод, поданный как факт, — это класс `fabricated-verifiable-specific`.

2. **У каждого утверждения о НАШЕМ коде есть адрес `путь/файл.tsx:строка`.**
   «У нас этого нет» без прогона поиска — не результат. И искать надо по синонимам,
   а не по одному слову: у нас та же вещь может звать себя иначе.

3. **Раздел «чего не проверил и почему» обязателен.** Непроверяемое называется вслух.
   Молчание читается как «проверено всё» и поэтому является враньём по умолчанию.

4. **Результат — ФАЙЛ в проекте, а не только сообщение в чате.** Чат стирается,
   документ остаётся и его можно перечитать через месяц.

5. **Перед сдачей — прогон проверки:**
   ```
   node ~/.claude/jidoka/scripts/research-audit.mjs --doc <документ> --tier light|deep
   ```
   Он считает утверждения без источника, утверждения о коде без адреса и отсутствующие
   обязательные разделы. Красный — чинить, а не объяснять.

## 3. Лёгкий уровень — «сделай ресёрч»

Цель: за один заход дать ответ, на который можно опереться, не разворачивая войну агентов.
Ориентир 4–6 агентов, минуты, а не полчаса.

```
1. ТРИ ЛИНЗЫ РАЗВЕДКИ, параллельно и независимо.
   Линзы подбираются под вопрос, но одна из трёх ВСЕГДА «наша сторона»
   (наш код, наши доки, наши данные) — иначе ресёрч выйдет про чужой продукт,
   а не про наше решение.

2. ЗАМЕР одним агентом.
   Всё, что разведка назвала кандидатом, проверяется по факту: в репозитории,
   в живой базе, в реальном ответе API. Статус: есть / частично / нет / непроверяемо.
   Статус «есть» без адреса файла автоматически понижается до «непроверяемо».

3. ОДНА ПРОВЕРКА НА ОПРОВЕРЖЕНИЕ вместо дебатов.
   Один скептик, которому дано задание СЛОМАТЬ вывод: где мы обманулись,
   что уже существует под другим именем, какой источник слабый.
   При сомнении скептик по умолчанию говорит «опровергнуто» — так дешевле.

4. ВЫВОД: 5–15 пунктов, каждый с приговором и первым шагом.
   Суда как отдельной фазы нет — приговор выносит основная сессия.

5. КРИТИК ПОЛНОТЫ — короткий, обязательный.
   Что не прочитано, какие утверждения без адреса, какой линзы не было.
```

Лёгкий уровень ПОВЫШАЕТСЯ до тяжёлого прямо посреди работы, если замер показал,
что дыр больше пятнадцати или что вопрос упирается в архитектуру. Повышение
называется владельцу вслух: «это оказалось глубже, поднимаю уровень».

## 4. Тяжёлый уровень — «дип-ресёрч»

Ориентир 12–16 агентов. Потолок объявляется ДО запуска; если тем больше, чем влезает,
режется охват, а не глубина, и отрезанное называется вслух (`log()` в прогоне).

```
1. РАЗВЕДКА — 5–7 линз, параллельно и независимо.
   Обязательные линзы: (а) сущности и модель данных чужого продукта,
   (б) его механика и синтаксис (переменные, шаблоны, правила),
   (в) его границы (API, лимиты, тарифы — тариф показывает, что ОНИ считают ценностью),
   (г) НАШ фактический инвентарь по коду,
   (д) соседи по рынку — за архитектурными решениями, не за фичами.
   Каждый разведчик возвращает и «чего по моей линзе проверить не удалось».

2. ЗАМЕР — по группам, каждый кандидат проверяется в коде или в живых данных.
   Числа и пути обязательны. Рассуждение не считается.

3. ДЕБАТЫ ВСЛЕПУЮ. Обвинение и защита работают ОДНОВРЕМЕННО и видят ТОЛЬКО замер,
   никогда доводы друг друга. Если стороны видят друг друга, они подстраиваются
   под чужую формулировку, и спор превращается в согласование.

4. СУД — приговор по фактам замера, а не по красноречию сторон.
   Замер сильнее любого довода: если проверка показала, что возможность у нас уже есть,
   приговор «отклоняем», как бы хорошо защита её ни расписала.
   Приговор обязан нести: вердикт, приоритет, причину, ПЕРВЫЙ ШАГ с путём к файлу,
   и СТОИМОСТЬ — делается ли это без правки чужого бэкенда и сколько занимает.
   Приговор без стоимости не решение, а пожелание.

5. КРИТИК ПОЛНОТЫ — обязательная фаза, не «уместный приём».
   Сверяет имена кандидатов на ВХОДЕ разведки с именами в приговорах и называет
   пропавших поимённо. Кандидаты, тихо исчезнувшие между фазами, — типовая утечка.

6. ДОКУМЕНТ в проект + прогон research-audit.
```

Плюс по месту: судейская коллегия из нескольких голосов на спорном пункте,
несколько попыток с выбором лучшей, повтор разведки до сухого круга.

## 5. Чего этот скилл НЕ делает

- Не строит. Как только владелец сказал «делай» — это `dev-pipeline`, а не ресёрч.
- Не подменяет сверку документа-синтеза. Если источники это ФАЙЛЫ (транскрипт, анкета,
  выгрузка), сверх research-audit гоняется `synthesis-coverage-audit.mjs` — он
  сравнивает документ с источниками, а research-audit смотрит только внутрь документа.
  Разные оси, обе нужны.

## Композиция

- «Ресёрч не сдаётся без собственного аудита покрытия» — `RESEARCH_COVERAGE_SELF_AUDIT.md`
- «Документ-синтез не сдаётся без сверки с источниками» — `SYNTHESIS_COVERAGE_GATE.md`
- «A specific you inferred is not a fact» — `NO_FABRICATED_SPECIFICS.md`
- «Такого нет — только после проверки ВСЕХ копий кода» — `MULTI_REPO_CANONICAL_SOURCE_DECAY.md`
